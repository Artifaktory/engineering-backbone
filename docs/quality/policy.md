# Versioned quality policy

This extends the canonical core policy. In this reference layout that policy is
`docs/agent-governance/core.md`; legacy Copier consumers retain `.engineering-backbone/core.md` and
their own stricter authoritative instructions. The quality catalog does not replace
authorization, role separation, review stops or human merge/release approval.
The optional quality package adds these obligations when a project adopts its
active profile. Legacy absence and an inactive installation seed do not activate
quality checks; all existing core and stricter project duties remain binding.

The dependency compatibility policy is `docs/quality/dependencies.md` in the source and
`.engineering-backbone/dependency-policy.md` when installed. It defines reviewed
resolution, supported combinations, update freedom and actual compatibility
evidence. Its optional project-owned `dependencies.json` adopts structural duties
per component through the existing navigation and workflow contracts; an inactive
seed does not activate them. Native manifests and resolution files remain version
authority. Shared Backbone tooling versions are not application-version mandates.

## Selection and authority

An adopting project selects a reviewed Backbone commit and catalog version in
`.engineering-backbone/quality-profile.json`. The `baseline` profile is mandatory
when active. Select `software` for executable software, language profiles for the
affected components, `high-risk` for material control-plane or other high-risk
work, and `agentic` for systems whose behavior includes agent delegation and
orchestration. The project quality plan records the selection and exclusions.
Selection suitability is independently reviewed; the structural guard does not
infer product domain, detect languages or certify the completeness of selection.

The catalog contains organization-owned rules with stable IDs and explicit
versions. Its ISO/IEEE/IEC references identify public editions and scopes only.
They do not assert full-text clause adoption or normative conformance. Public
Microsoft and client guidance informs bounded rules. C++17 and IEC profiles are
disabled references until a separate integration reviews applicability, source
access, concrete obligations, tooling and qualified human ownership.

Version 1 accepts the compiler-owned current catalog. A project cannot supply
alternative catalog authority, edit managed catalog bytes or weaken an active
inherited selection or automatic check binding through a candidate change.
Retaining additional historical catalogs requires a separately reviewed trusted
source allowlist. Changes are adopted through reviewed project PRs; do not update
rules or downstream projects automatically.

## Technology selection and document routes

The versioned technology extension at `.engineering-backbone/standards/technologies/`
in both the reference layout and legacy consumers adds bounded
language, platform, runtime and framework obligations under this same authority.
It preserves the original quality catalog; it is not an alternative baseline.
Select only applicable components through `.engineering-backbone/navigation.json`.
Selected `TECH-*` rules are mandatory and bind actual PR check IDs; required quality
profiles remain additive. Recommendations are defaults with documented technical
reasons for deviation. Free choices remain within the agent's authorized scope,
without a new approval requirement solely for a routine implementation decision.
The general `cpp` technology profile does not activate the older disabled `cpp17`
or IEC reference profiles, or imply complete adoption of an external style guide.

Active navigation requires active quality and workflow contracts and a reviewed,
complete inactive routing seed followed by an enabled-only activation PR. Resolve
its scoped request with the approved guard and actually read the resulting policy,
project, role/task and component documents before scoped work. Verify the complete
context again at handoff; resolve a new request for changed role, scope or snapshot.
Missing or invalid mandatory context blocks the affected task. Retain stricter
project instructions and investigate unexpected overrides before proceeding.

Routing and hashes establish structural context integrity for declared inputs.
They do not prove native instruction loading, semantic compliance, authenticated
revisions or execution. Verify those with actual client observations, project tests
and independent review. Source guidance is `docs/agent-governance/agent-navigation.md`; installed
guidance is `.engineering-backbone/navigation-guide.md`. Preserved native files
need reviewed manual integration of changed routing instructions during adoption.

## Role and phase contract

Use the existing Task Packet roles. Architecture, security, testing, documentation
and orchestration are bounded responsibilities within those roles, not new schema
roles. Planning selects applicable rules and measurable acceptance. Implementers
produce scoped code, tests and documentation. Quality checkers execute checks and
record results. Independent reviewers assess semantic obligations on a frozen
snapshot. Triage classifies findings before any repair.

Before each delegation, include the exact profile/catalog/rule versions, task and
acceptance IDs, affected design context, authorized actions, expected artifacts,
required checks and stop/return conditions. Verify the intended client's actual
instruction loading and supported capabilities. A provider instruction file or
agent reply alone does not prove context loading, compliant behavior or test PASS.

Apply design review before material design/implementation changes. Apply test
planning during planning and update it as risks or behavior change. Apply code and
documentation rules during implementation. Obtain required deterministic results
before independent Full review; use triage, confirmed repairs and scoped Delta
reviews as defined by the core policy. Preserve local publication and human gates.

For architecture-specific obligations, follow the architecture contract referenced
by the project's adopted canonical core. Updating this optional quality package
alone does not adopt a newer core policy. The architecture contract's document
rule IDs are not new quality-catalog rules or automatically installed checks.
Preserve the existing quality profile and traceability CSV schema; link architecture
records through their existing fields.

Planning and decomposition follow the planning contract referenced by the
project's adopted canonical core. Updating this optional quality package alone
does not adopt a newer core. Include applicable quality/security work, verification
environments, integration and evidence ownership in the delivery plan; carry
existing rule and check IDs through linked records without extending the profile
or traceability CSV schema.

## Tests and evidence

Maintain a project quality plan, test strategy and rule-to-requirement/risk
traceability. Keep established requirements and architecture at their existing
authoritative paths; link to them instead of creating duplicate specifications.
Select relevant unit/component, integration/contract, critical acceptance,
negative/boundary, regression and security tests. Add performance, migration,
recovery and platform coverage where project risks make them necessary.

For agentic systems, verify the supported complete handoff chain and relevant
failure, authority, state and pause/resume paths. Worker-only tests do not establish
orchestrator/instructor behavior. Real provider-dependent checks and deterministic
stubbed checks have different scopes; label both and retain any unexecuted coverage.

Coverage includes requirements, material risks, critical behavior and appropriate
technical code/branch measurements. Set and justify component thresholds and
excluded areas locally; no universal percentage is imposed. A high percentage,
schema-valid matrix or check name does not establish test quality or correctness.

Actual check commands remain in the workflow kit. Bind applicable rule check groups
to concrete PR check IDs. Each group requires at least one bound kind from that
group. `QUAL-TEST-001` allows a `test` or `docs` check for the baseline; executable
software and agentic refinements require tests. This allows a documentation-only
project without treating a documentation check as proof of executable behavior.

Structural validation verifies declared contracts, safe paths, required artifacts
and check bindings. Actual check execution, result integrity, semantic review and
repository required-check/human controls remain separate obligations. Missing,
failed, blocked or unexecuted mandatory evidence blocks the declared completion
gate. Never relabel it as passed to publish or release.

## Exceptions and certification

Baseline rules are nonwaivable. A refinement marked `waivable` may have a bounded,
unexpired project exception recording the rule, reason, owner, human approval,
expiration and compensating measure in the profile and exception document. An
approval reference is a declaration for independent review, not an authenticated
signature supplied by the guard. Preserve stronger local exception requirements.

The framework produces traceable organizational quality evidence. Formal
certification requires a specific scheme, full applicable normative material,
qualified assessment and its required independent evidence. Do not advertise
certification or clause conformance from structural PASS or agent review.
